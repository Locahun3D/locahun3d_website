01 なぜ3DGSをIsaac Simに持ち込むのか

私はロケハン3Dで、都市部を中心にした3DGSスキャンデータを制作・販売しています。映像制作の素材として使うならUE5に持ち込むのがいちばん自由が利きますが、用途が変わると行き先も変わります。ロボット・自律移動・センサーシミュレーションを扱うなら、NVIDIA Isaac Simが本命です。

  • 実在の場所でロボットを動かせる ── CGで作り込んだ架空の街ではなく、実際にスキャンした渋谷の路上をそのままシミュレーション環境にできます。
  • 物理シミュレーションと同居できる ── PhysXの剛体・関節・センサーを、実写ベースの背景の中で動かせます。
  • センサーの学習データを作れる ── 実在の街並みを背景にしたカメラ画像を、任意のアングル・任意の時間帯で無限に生成できます。

Isaac Sim 6.0はガウシアンスプラットをネイティブに描画できます。RTXのパストレーシングに参加するため、被写界深度やモーションブラーもそのまま効きます。ただし実際に大規模スキャンを流し込むと、ドキュメントに書かれていない壁にぶつかります。この記事の主題はそこです。

02 用意するもの

Isaac Sim
6.0.0（Windows standalone zip・約9.94GB）。展開後は約40GBになるので、空き50GBを見ておきます
スキャンデータ
XGRIDs PortalCamで取得した .lcc2（渋谷スクランブル交差点・3,523万点）
変換ツール
PlayCanvas splat-transform（npm・無料）。npm install -g @playcanvas/splat-transform
USD変換
omni.kit.converter.gsplat。Isaac Sim 6.0に標準同梱されているので追加インストールは不要です
なぜPLYではなく.lcc2から始めるのかXGRIDsの .lcc2 は単なる点群ファイルではなく、オクツリー分割されたLODチャンク、衝突用メッシュ、そしてスキャン時のカメラ軌跡を含むパッケージです。後半で使うカメラ配置は、この軌跡データがあるかどうかで手間がまったく変わります。PLYだけを渡されている場合でも手順は同じですが、.lcc2 があるならそちらを使ってください。

Isaac Simの導入自体は、zipを展開して post_install.bat を実行するだけです。インストール先は C:\Program Files を避けます。Isaac Simは動作中にデータを書き込むため、管理者権限が必要な場所に置くと余計なトラブルを招きます。

03 最大の落とし穴：1プリム1,677万点の描画上限

ここが今回いちばん時間を溶かしたポイントです。先に結論を書きます。

Isaac SimのRTXレンダラーは、1つのプリムあたり224（16,777,216）点までしか描画できません。これを超えるとレイトレーシング用の構造（TLAS）の構築に失敗し、そのプリムは1点も表示されなくなります。しかも変換ツールにもPython APIにもエラーは一切出ません。「変換は成功、点数も正しい、なのに画面は真っ暗」という状態になります。

渋谷のデータは17,201,445点でした。上限をわずか42万点、率にして2.5%超えていただけです。この状態でも convertPlyUSD は正常終了し、USDファイルには17,201,445点すべての座標・スケール・不透明度・色が正しく書き込まれ、ステージに配置すればプリムの型も ParticleField3DGaussianSplat として認識されます。表示だけが行われません。

この上限は公式ドキュメントに記載がありません。判明したのは、Isaac Simのログファイルに残っていた次の1行からです。

[Error] [rtx.scenedb] Failed to create TLAS for /World/ShibuyaSQ

さらにレンダラーのバイナリ（rtx.scenedb.plugin.dll）を文字列検索すると、上限そのものを説明するメッセージが埋まっています。

Max gaussian count has to be less than 2^24 for every prim.
Skip loading the excessive gaussians...
Please break the asset into separate...

つまり「点数を減らすか、複数プリムに分割しろ」というのが仕様上の正解です。この記事では前者を採ります。渋谷のデータで必要な削減はわずか2.5%なので、見た目への影響はほぼありません。

読み込みが成功したかを確認する方法ステージに配置したあと、Isaac Simのログ（~/.nvidia-omniverse/logs/Kit/Isaac-Sim Full/6.0/）を Gaussian prim loaded で検索します。Gaussian prim loaded: /World/Shibuya, count=16500000 のように出ていれば描画対象として登録されています。代わりに Failed to create TLAS が出ていれば、そのプリムは表示されません。ビューポートを見る前にここを確認するのが確実です。

04 LCC2から間引いてPLYを書き出す

splat-transformで点数を上限未満に落とします。--decimate に絶対数を渡すことで、指定した点数まで削減できます。

npm install -g @playcanvas/splat-transform

splat-transform ShibuyaSQ.lcc2 -d 16500000 shibuya_16m.ply

この処理は単純な間引きではなく、近接するガウシアンを段階的にペアマージしていく方式です。ランダムに削除するより情報の欠落が少なく、16,500,000点まで落としても見た目の劣化はほとんど分かりません。手元の環境（RTX 5090）で約3分、出力は881MBでした。

使ってはいけないオプション浮遊ゴミを除去する --filter-floaters は魅力的に見えますが、大規模データでは使えません。この処理はWebGPU経由でGPUバッファを確保するため、2GBのバッファ上限に当たって失敗します（渋谷のデータでは2.2GBを要求して停止しました）。また --decimate は必ず最後のアクションで、出力は .ply である必要があります。

05 USDに変換してステージに配置する

Isaac Simに同梱されている omni.kit.converter.gsplat でPLYをUSDへ変換します。Isaac Sim内のPythonから次のように呼び出します。

import omni.kit.app
omni.kit.app.get_app().get_extension_manager() \
    .set_extension_enabled_immediate("omni.kit.converter.gsplat", True)

from omni.kit.converter.gsplat import convertPlyUSD
convertPlyUSD(r"shibuya_16m.ply", r"shibuya_16m.usdc")
出力は必ず .usdc にする拡張子を .usdz にすると、内部レイヤーがテキスト形式（.usda）になってファイルサイズが2倍以上に膨れます。バイナリ形式の .usdc を指定してください。16,500,000点で約8分・1.07GBでした。

ステージへの配置では、参照する前に既存のガウシアンスプラットを掃除します。古いテスト資産が残っていると、「新しいデータの一部だけが表示されている」ように見えて原因の切り分けが極端に難しくなります。実際に私はこれで数時間を失いました。

import omni.usd
stage = omni.usd.get_context().get_stage()

# 既存のガウシアンプリムを全削除
for p in list(stage.Traverse()):
    if p.GetTypeName() == "ParticleField3DGaussianSplat":
        stage.RemovePrim(p.GetPath())

# 型を指定せず OverridePrim で参照する
prim = stage.OverridePrim("/World/Shibuya")
prim.GetReferences().AddReference(r"shibuya_16m.usdc")
DefinePrimではなくOverridePrimを使うstage.DefinePrim(path, "Xform") のように型を明示してから参照を追加すると、ローカルの型指定が参照先より強く効いて ParticleField3DGaussianSplat 型が失われます。属性は入るのにプリムの型がXformのままになり、当然描画されません。型を指定しない OverridePrim で作成してください。

06 上下反転を補正する

convertPlyUSD は上方向の軸を指定できますが、Y-upを指定して変換すると元がZ-upのスキャンデータは上下逆さまになります。建物が地面から下向きに伸びる状態です。

これに気づかないまま「上空から見下ろす」つもりでカメラを置くと、地面を裏側から見ることになり画面は真っ暗になります。プリムにX軸まわりの−90度回転を適用することで、元のZ-upの向きに戻ります。

from pxr import UsdGeom

x = UsdGeom.Xformable(prim)
x.ClearXformOpOrder()
x.AddRotateXOp().Set(-90.0)

座標の対応関係は USD(x, y, z) = 元データ(x, -z, y) です。この補正を入れておくことで、次に使うスキャン軌跡の座標をそのまま流用できるようになります。

07 スキャン軌跡を使ってカメラを置く

ここが実用上のいちばんのコツです。カメラ位置は自分で計算せず、スキャン時に実際に歩いた軌跡をそのまま使います。

.lcc2 に含まれる info/poses.json には、スキャン中の姿勢データが記録されています。渋谷のデータでは30,791点の位置・回転が入っていました。この座標は元データのZ-up系そのままなので、前節の補正を済ませていればそのまま使えます。

import json
poses = json.load(open("info/poses.json", encoding="utf-8"))
# fusionPoses[グループ][フレーム]["T"] = [x, y, z]

あとは軌跡上の1点を選び、目線の高さ（1.7m前後）にカメラを置いて水平方向を向けるだけです。向きの計算には Gf.Matrix4d().SetLookAt(eye, target, up).GetInverse() を使い、AddTransformOp() に設定します。この形なら転置の間違いが起きません。

from pxr import Gf, UsdGeom

eye    = Gf.Vec3d(35.28, -22.05, 1.7)   # 軌跡上の1点＋目線の高さ
target = Gf.Vec3d(-10.0,  20.0, 12.0)

xf = Gf.Matrix4d().SetLookAt(eye, target, Gf.Vec3d(0,0,1)).GetInverse()
cx = UsdGeom.Xformable(cam_prim)
cx.ClearXformOpOrder()
cx.AddTransformOp().Set(xf)

この方法が効くのは、スキャンした人が歩いた場所こそ、そのデータがいちばん高密度に記録されている場所だからです。撮影範囲の外にカメラを置くと、建物の裏側など、そもそも撮影されていない面を見ることになります。

カメラ位置の違い同じデータでも、カメラを置く場所で結果がまったく変わります。

俯瞰が必要な場合も、いきなり数百メートル上空に飛ばすのではなく、軌跡上から少しずつ引いていくのが確実です。バウンディングボックスから自動でカメラ距離を計算する方法は、疎な外れ値に引きずられて機能しません。渋谷のデータでは全体の範囲が484m×528mと算出されましたが、実際に密度がある範囲はその一部でした。

描画の待ち時間1,650万点のRTX収束には時間がかかります。キャプチャ前に await app.next_update_async() を150フレーム以上回してください。待ちが足りないと真っ黒な画像が保存されます。またビューポートのキャプチャはIsaac Simのウィンドウを前面にしておくほうが安定します。

08 現状の限界

実際に運用してみて分かった制約を挙げます。

  • スプラット単体では物理判定を持ちません。 ガウシアンスプラットは見た目のデータであり、PhysXの当たり判定はありません。ロボットに障害物として認識させるには、別途メッシュを用意してコリジョンを設定します。.lcc2 には衝突用メッシュが同梱されているので、これを流用するのが早道です。「スプラット＝見た目、メッシュ＝物理」という役割分担が公式のアーキテクチャです。
  • 自動フレーミングは当てになりません。 バウンディングボックスは疎な外れ値まで含むため、そこからカメラ距離を計算しても機能しません。frame_viewport_prims もIsaac Sim 6.0では引数の不一致で呼び出せませんでした。前節の軌跡ベースの配置が現実的です。
  • ストリーミングLODはありません。 Locahun3Dのビューアーが持つような、視点に応じてチャンクを読み込む仕組みはIsaac Sim側にはなく、1ファイルを丸ごとGPUに載せます。都市を広範囲に扱う場合は、ロボットが動く範囲を事前に切り出すほうが現実的です。
  • スプラットの編集機能はありません。 不要な点の削除や色の調整は、Isaac Simに入れる前の工程（splat-transformなど）で済ませておきます。
画面が真っ暗になったときの切り分けまずスプラットを非表示にしてグリッドが表示されるかを確認します。グリッドも出ないならレンダラー側の問題なので、Isaac Simを再起動するのがいちばん早いです。グリッドが出るならカメラの位置か向き、あるいは点数上限を疑います。

09 まとめ

手順としては、XGRIDsの .lcc2 をsplat-transformで1,677万点未満に間引き、.usdc に変換してステージへ参照配置し、上下反転を補正して、スキャン軌跡の座標にカメラを置く、という一本道です。

いちばん重要なのは点数上限（224）です。ここを超えているとエラーが出ないまま何も表示されないので、原因の切り分けが極端に難しくなります。読み込み後にログで Gaussian prim loaded を確認する習慣をつけておけば、この罠は避けられます。

もうひとつはカメラをスキャン軌跡の上に置くことです。バウンディングボックスからの自動計算に頼らず、実際に歩いた座標をそのまま使う。これだけで、看板の文字が読める品質のショットが最短で得られます。

Isaac Simと組み合わせれば、実在の街並みをそのままロボットや自律移動の検証環境にできます。用途に応じてUE5と使い分けるのが現実的で、映像素材としての出力はUE5×XGRIDs SDKの記事にまとめています。3DGSの活用について気になることがあれば、お気軽にお問い合わせください。
